## K05 — retrieval benchmark (live Postgres)

Set: `tests/fixtures/okf/context-benchmark.json` — a workspace pack of 17 multi-section documents
with 8 internal links (ITSM and sales) and **32 questions** labelled with the answering section
(`path#anchor`), in four types: direct (7), paraphrase (8), section — the answer is not the first
section (9) — and hop — the question names a document that *links* to the answer's (8). Written
by the implementer before any configuration was run; small and not held out. Scope: the benchmark
pack only. Run: `tests/integration/test_knowledge_k05_k08.py::test_retrieval_benchmark_before_and_after`
with `ANALYSTOS_CONTEXT_BENCH_OUT=<file>` (code: `src/analystos/context/benchmark.py`).

Compiler configurations count only what passes the relevance gate (what can reach a prompt).
T03 sends the first 240 characters of a *whole document*, so it is credited with a section only
when that excerpt contains it; K05 sends sections.

| configuration | doc R@1 | doc R@3 | doc MRR | section R@3 | section MRR |
|---|---:|---:|---:|---:|---:|
| index, K01 (`ts_rank_cd` + vector, RRF) | 0.656 | 0.969 | 0.800 | 0.844 | 0.762 |
| index, BM25 + vector, RRF | 0.656 | 0.969 | 0.810 | 0.938 | 0.780 |
| index, BM25 + vector + one hop | 0.656 | 0.969 | 0.813 | 0.969 | 0.790 |
| **compiler before (P4-T03)** | 0.750 | 0.938 | 0.848 | 0.938 | 0.679 |
| **compiler after (P4-K05)** | 0.750 | 0.938 | **0.855** | 0.938 | **0.780** |

By question type (doc MRR / section MRR):

| type | T03 | K05 | index K01 | index BM25+hop |
|---|---|---|---|---|
| direct (7) | 1.000 / 1.000 | 1.000 / 1.000 | 1.000 / 0.929 | 1.000 / 0.929 |
| paraphrase (8) | 0.891 / 0.883 | 0.900 / 0.896 | 0.792 / 0.781 | 0.792 / 0.792 |
| section (9) | 1.000 / **0.500** | 1.000 / **0.833** | 1.000 / 1.000 | 1.000 / 1.000 |
| hop (8) | 0.500 / 0.396 | 0.521 / 0.410 | 0.407 / 0.330 | 0.458 / 0.431 |

Second set, the P4-K10 paraphrase questions over the platform pack (36 questions, 18 documents,
document level, index only): `ts_rank_cd` + vector MRR **0.924** → BM25 + vector **0.938**
(R@1 0.889 → 0.917).

Honest reading:

* The clear gain is **section-level**: T03 truncates a whole document to 240 characters, so for
  questions answered by a later section it sends the document but not the answer (section MRR
  0.50); K05 sends the section (0.83). Document-level ranking is essentially unchanged
  (0.848 → 0.855).
* BM25 over `ts_rank_cd` is a small gain on both sets (doc MRR +0.010 / +0.014; section R@3
  0.844 → 0.938).
* **One hop helps little as shipped.** A first version let a linked document's score be *added
  without a ceiling* (hop decay 0.25): hop questions went from doc MRR 0.428 to 0.896, but direct
  questions fell 1.000 → 0.905 and paraphrases 0.813 → 0.698 (a linked rule overtook the
  definition that links to it), overall 0.810 → 0.831. The shipped rule — a hop never lifts a
  section above the hit that links to it — was chosen on that principle *after* seeing both runs
  on this same set (a selection effect): overall 0.813, hop 0.458, no loss on direct questions.
  In the compiler a hop mainly *admits* linked context that has no word overlap with the question.
* The K01 `ts_rank_cd` numbers vary by ±0.005 between runs: its ties are broken by section id,
  which is derived from a per-install pack id. BM25 scores did not tie on this set.

## K05 — episodes cannot crowd out glossary terms; external knowledge in prompts

`tests/unit/test_context_k05.py::test_episodes_cannot_crowd_out_glossary_terms`: 30 maximally
relevant episodes listed *before* the glossary in the profile, 4,000-char budget — the glossary term
is sent, episodes stay within their 12% share (`section share` in the omitted list), and the prompt
keeps the profile's section order. `test_memory_is_given_back_before_glossary_when_the_budget_is_short`:
glossary items are never dropped while a memory item is still in the prompt.
`test_external_provider_results_are_their_own_untrusted_section` and the integration test
`test_compiler_over_pack_sections_with_receipts_external_and_episodes`: the run's context-package
`external` results (K09) become an `external` section marked `trusted: false` with the provider's
receipt; pack sections carry `path`, `anchor`, document and section sha256 in their receipts.

## K07 — review queue (live Postgres)

`tests/integration/test_knowledge_k05_k08.py`:

* `test_review_queue_batch_approve_edit_reject_writes_one_revision` — three model drafts with
  per-field value/confidence/provenance; an analyst cannot decide (403); the owner's batch
  (approve, edit-then-approve, reject) writes **one** workspace-pack revision; approved documents
  are human-reviewed OKF with each field's provenance (edited field `source: human`, untouched
  field keeps `source: rule`); the rejection is a `negative/` document that `load_knowledge`
  returns in `negative_knowledge`; deciding again reports `not_pending`; the rejected content is
  never proposed again.
* `test_drafts_never_overwrite_owner_content` — proposing over an owner document is skipped;
  approving after an owner wrote the path meanwhile is refused (`owner_content_exists`), the owner
  text is unchanged.
* `test_crawler_enrichment_queues_drafts_and_avoids_rejected_text` (**mock** router, real crawler
  code path `_enrich_batch`) — the model's description fills the placeholder and is queued with
  model id, purpose, prompt version `crawl-enrich-v2`, crawl run, confidence 0.95 capped to 0.9, and
  the previous value; rejecting restores the placeholder; the next crawl sends the rejected text as
  `rejected` and drops a repeat; a different description is approved, sets the catalog description
  and marks the asset reviewed.

## K08 — learning loop (live Postgres)

* `test_accepted_finding_becomes_a_draft_attested_computation` — `POST /api/insights/{id}/outcome`
  `accept` on a verified finding returns a draft; its computation holds `query_hash` (sha256 of the
  SQL), `result_hash`, `q_value` 0.0004 (BH-adjusted), `effect_size` {0.31, cramers_v},
  `verified_by: process:analystos-rev`, `stale_after`; a lineage edge `derived_from → insight`.
  Approved, the pack document validates as an Attested Computation (`attested.validate`), status
  `stable`, `verified` = REV then the human reviewer. An unverified finding is not drafted.
* `test_approved_kpi_and_user_feedback_become_drafts` — approving a semantic metric (separation of
  duties, real approval path) drafts a `Metric` document with the approval id as provenance and
  the source columns as `mapped_columns`; run feedback `add_context` / `redirect` /
  `reject_finding` become `note` / `note` / `negative` drafts; `question` drafts nothing.
