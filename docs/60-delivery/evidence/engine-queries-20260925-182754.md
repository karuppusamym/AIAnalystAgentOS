## What changed

- **`get_state`** reads the run and its tasks without locks. Only a poll that must change state
  (pause, a run status, parking a task at WAITING_USER, skipping a task) takes the run's row lock
  and decides again on fresh rows — the extra two reads in the transition row, paid once per status
  change. Several gated tasks' approvals are read in one `IN` query.
- **Claims are optimistic.** `run_task.claim_version` (migration `0016`) is bumped by every claim;
  a claim is `UPDATE run_task SET status='RUNNING', attempts=attempts+1, started_at=now(), error=NULL,
  claim_version=:v+1 WHERE id=:id AND claim_version=:v AND status=:seen AND plan_version=:seen` and
  wins only with rowcount 1. The read joins the run's workspace id (one statement fewer). The
  `CLAIM_TTL_SECONDS` rule is unchanged: a RUNNING task whose `started_at` is younger than the TTL
  is `in_progress`; an older one, or one released by `release_timed_out_claim` (`started_at=NULL`),
  is retaken. The completion write keeps its row lock (a state transition) and drops the result of
  an attempt whose claim was retaken (`superseded`); a crashed attempt resets the task only if it
  still holds the claim.
- **`lineage_for`** is one recursive CTE per artifact, bounded by depth and filtered to the
  workspace, instead of loading every edge of the workspace. A new index
  `ix_lineage_edge_workspace_to (workspace_id, to_type, to_id)` serves the `to` end (the unique key
  serves the `from` end). EXPLAIN ANALYZE on a workspace of 5,003 edges: 27.9 ms with a
  UNION-of-ends draft (hash join over the workspace's edges per iteration), **0.26 ms** with the
  committed OR-join form (bitmap-OR of both indexes per reached node).
- **`resolve_scope`** reads selected assets of all in-scope sources in one query and their columns
  (ordinal order) in a second, instead of one query per source and one per asset; the workspace is
  read once instead of twice.

## Tests

- `tests/integration/test_engine_queries.py` — the table above and its bounds.
- `tests/integration/test_engine_claims.py` — 6 threads race on one task (every thread reads before
  any writes) for a NEW task, an expired claim and a claim released by `release_timed_out_claim`:
  exactly one claim wins, the rest get `in_progress`; 6 concurrent `execute_task` calls run the
  agent once; a hung attempt superseded by its retry cannot overwrite the retry's result.
- `tests/unit/test_lineage_unit.py` — the CTE returns exactly what the former BFS returned, for
  depths 0–6 on random graphs with cycles and a second workspace (SQLite).
- `tests/unit/test_engine_unit.py` — the unlocked/locked `get_state` passes, claim version,
  superseded result, crash of a superseded attempt, retaking a released claim.
- Migration `0016` upgraded, downgraded to `0011` and upgraded again on a scratch database.

**Results (2026-09-25):** ruff clean; fast suite green; full `-m integration` green except two
environmental failures on a host at load average 13–19 on 4 cores shared with parallel sessions:
`test_workspace_isolation.py::test_migration_0007_…` ("too many clients", passes on re-run) and
`test_temporal_queues.py::test_a_hung_statistics_task_is_detected_within_its_heartbeat_window`
(the heartbeating `test:slow` probe is retried after `BrokenProcessPool`). That test uses a probe in
place of the engine, and it fails the same way on unmodified `0022154` on the same host.
`test_e2e_local_run.py`, governance, isolation and graph tests pass.
