# Load tests against the spec v3 §8 targets — 2026-09-25 (P4-S05)

**What this is.** Measured results of `scripts/load/` on this development machine's compose stack
(4 cores, 16 GB, no swap; Postgres 16 with `max_connections = 100`, Temporal and Redis in compose),
**shared with other agent sessions running test suites at the same time** (load average 6–17 before
our runs started). Every run used its own isolated plane (control DB, analytics DB, role prefix,
Temporal task-queue prefix, Redis budget prefix; `scripts/load/harness.py`) and dropped it
afterwards. No model was called: `OPENROUTER_API_KEY` was empty, so every LLM purpose ran its
deterministic path.

**What this is not.** Not a four-node deployment, not production hardware, not PgBouncer, not uvloop
for the SSE server. A target marked *not met* here is what this machine reached, with the limit that
stopped it; it is not a claim about a sized deployment. Raw JSON is next to this file.

## Summary

| §8 target | Result on this machine | Verdict |
|---|---|---|
| SSE event latency < 1 s at p95 with **500** open streams | p50 19.7 ms, **p95 154 ms**, p99 1.08 s, max 1.37 s; 15,000/15,000 deliveries in order; 50/50 Last-Event-ID resumes complete; 500/500 `end` frames; no errors | **Met** |
| **1,000 workspaces** | 1,000 created through the API (p50 143 ms, p95 229 ms, 123/s); read mix from 32 clients: 125 req/s, **p50 197 ms, p95 654 ms**, 0 errors; workspace list of 1,000 p95 993 ms; tenancy holds (10/10 listed, 50/50 foreign refused) | **Met after a fix** (the list endpoint timed out before it; see below) |

## 1. 500 SSE streams — `sse-load-20260925-232837.{md,json}`

`python scripts/load/load_sse.py` (wraps the P4-C04 `scripts/load_sse.py`: `--streams 500 --runs 50
--seconds 30 --reconnect 50`, private uvicorn on stdlib asyncio, Redis nudges on). 6/6 checks passed.

| Measure | Value |
|---|---|
| Events emitted / deliveries expected / received | 1,500 / 15,000 / 15,000 |
| Commit→client latency p50 / p95 / p99 / max | 19.7 / 154.4 / 1,084.6 / 1,369.7 ms |
| Server loop lag p50 / p95 / p99 / max | 0.47 / 5.7 / 22.4 / 175.6 ms (one probe sample > 100 ms, at connect time) |
| Slow-callback warnings (≥ 100 ms) | 0 |
| Full GC pauses > 20 ms | 22, 42, 51, 73 ms |
| Stream connect p95 (auth + headers, 500 at once) | 3.7 s |

The p99 above 1 s coincides with the full-GC pauses and the 500-connect burst; the target (p95) holds
with margin. Connect time under a 500-client burst is the slowest part.

## 2. 1,000 workspaces — `load-workspaces-20260925-233303-before-fix.json`, `load-workspaces-20260925-233550-after-fix.json`

`python scripts/load/load_workspaces.py --workspaces 1000 --concurrency 32 --seconds 30 --api-workers 2`.

**Finding (fixed).** `GET /api/workspaces` ran eight `COUNT(*)` statements *per workspace*
(`api/routers/workspaces.py::_summary`), i.e. 8,000 statements for 1,000 workspaces. Measured before
the fix: one uncontended list took **5.9 s**; under the 32-client mix every list request took 37–38 s
or timed out at 60 s (26 `ReadTimeout`s), and those requests starved the rest of the API
(read throughput **6.9 req/s**). The list now uses four grouped statements per 500 workspaces
(`_summaries`; `tests/integration/test_workspace_list_counts.py` asserts identical counts and a
statement count that does not grow with the number of workspaces).

| Measure | Before fix | After fix |
|---|---|---|
| Workspace create p50 / p95 (1,000 via API, 16 at a time) | 118 / 224 ms | 143 / 229 ms |
| Admin list of 1,000, uncontended | 5,860 ms | **125 ms** |
| Workspace list under load p50 / p95 | 36.9 s / 37.9 s (+26 timeouts) | **513 / 993 ms** |
| Read mix throughput | 6.9 req/s | **125.5 req/s** |
| Read mix p50 / p95 / p99 (all endpoints) | 267 / 670 ms / 36.2 s | **197 / 654 / 861 ms** |
| Slowest endpoint p95 (after) | — | workspace detail 724 ms, semantic 623 ms |
| Errors | 26 | 0 |
| Tenancy: analyst lists only their 10; 50 sampled foreign workspaces refused (403/404) | holds | holds |
| API processes RSS max / CPU mean | 498 MB / 123 % | 482 MB / 116 % |
| Machine load (1-min) mean / max during the run | 14.4 / 16.7 | 8.6 / 10.9 |

Per-endpoint p50 sits at 150–280 ms with the host at load 8–11 from other sessions; the uncontended
list (125 ms for 1,000 rows) is the better indicator of the query cost.

## 3. 50 concurrent runs — `load-runs-20260925-233642.json`

`python scripts/load/load_runs.py --runs 50 --workers 4 --deadline 360`: the ServiceNow mock's
`incident` table (20,000 rows) staged once (3.2 s); 4 `analystos worker` processes, each serving
every queue (analysis 8 threads, compute a 4-process pool); one baseline run alone, then 50
investigations started at once through `services.runs.create_run` (publication skipped) on Temporal.

| Measure | Value |
|---|---|
| Baseline run alone (on the 4 workers) | COMPLETED in 34.1 s |
| Submitted / submit p50 / p95 | 50 / 959 / 1,223 ms (all 50 in 1.7 s) |
| Start delay (created → RUNNING) p50 / p95 | 1.9 / 5.4 s (42 of 50 started) |
| Peak RUNNING at once | 38 (at t+10 s) |
| Completed / failed / unfinished at 360 s | **0 / 14 / 36** (unfinished were cancelled) |
| Failure causes | `required task(s) failed: context / metadata / profile` |
| Worker-log signals | 11,670 × `FATAL: sorry, too many clients already`; 1,117 activities failed after retries; 73 task crashes |
| Postgres connections to the run's control DB, max | 52 (plus analytics-DB pools; the compose server also serves Temporal ≈ 34 and other sessions) |
| Worker RSS (4 workers + compute pools) max / CPU mean | 5.8 GB / 224 % (max 360 %) |
| Machine load (1-min) mean / max | 25.5 / 39.2 |

**Bottleneck.** Connections, before CPU. Each worker process opens a control-plane pool of up to 30
connections (`db/base.py`: `pool_size=10, max_overflow=20`, not configurable), analytics pools per
identity of up to 10 (`gateway/engines.py`), and every compute-pool child opens its own. Four workers
want well over 100 connections; the shared server allows 100 in total. Once refused, steps fail
(`context`, `metadata`, `profile`) or retry until the run stalls. CPU would be the next limit: the
smoke run below needed ≈ 23 CPU-seconds per run, so 50 runs are ≈ 19 CPU-minutes — about 5 minutes
of this whole 4-core host even with no contention.

**Smoke calibration (same script, earlier the same evening, not a target run).** `--runs 3 --workers 1`:
3/3 COMPLETED, run time p50 32.3 s / max 34.7 s, baseline 19.0 s alone, peak Postgres connections 28,
worker RSS 1.9 GB, CPU mean 199 %. So the code path completes concurrently when connections suffice.

We did not re-run with fewer workers: at the time the shared server already had 89 of 100
connections in use by other sessions, and a second attempt would have broken their tests.

**What reaching the target needs (not done here).** PgBouncer in transaction mode in front of
Postgres (spec v3 §8 already names it) or a larger `max_connections` on a dedicated server;
configurable pool sizes for the control plane and the gateway engines (hard-coded today); and four
worker hosts rather than four processes on one 4-core host.

## Reproduce

```bash
PYTHONPATH=src .venv/bin/python scripts/load/load_sse.py                 # 500 streams, ~1 min
PYTHONPATH=src .venv/bin/python scripts/load/load_workspaces.py          # 1,000 workspaces, ~1.5 min
PYTHONPATH=src .venv/bin/python scripts/load/load_runs.py --runs 50 --workers 4 --deadline 360   # ~7 min
```

Each script provisions and drops its own plane (`--keep` keeps it), never touches the dev
databases, and writes its JSON here. Total load time today ≈ 11 minutes (SSE 1, workspaces 1.5 × 2,
runs 7).
