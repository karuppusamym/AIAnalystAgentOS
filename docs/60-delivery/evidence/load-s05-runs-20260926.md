# 50 concurrent runs, re-run with configurable pools and PgBouncer — 2026-09-26 (P4-S05)

Follows [`load-s05-20260925.md`](load-s05-20260925.md) §3, where 0/50 runs completed because four
worker processes wanted far more Postgres connections than the shared `max_connections = 100`
allowed (11,670 `too many clients` refusals). The SSE and 1,000-workspace results in that file still
stand and were not re-run.

**Machine.** The same development host: 4 cores, 16 GB, no swap, compose Postgres 16 with
`max_connections = 100`, **shared** with Temporal (28–44 connections), the dev stack (≈ 16) and
at times other sessions' test suites; 55–62 of the 100 connections were in use before each run below.
Before each attempt the host was idle (1-min load < 1) and no other session's test databases were
connected. **No model was called** (`OPENROUTER_API_KEY` empty: every purpose on its deterministic path).
Each attempt used its own plane (`scripts/load/harness.py`) and dropped it afterwards.

**Not** a four-node deployment: four worker processes (each serving every queue: analysis 8
threads, publish 4, crawl 2, elt 2, compute a 4-process pool) share 4 cores.

Fixes in code (all found by this load, none specific to it):

1. **Pool sizes are settings** per plane (`src/analystos/db/pools.py`, `core/config.py`): control
   (`ANALYSTOS_DB_*`, default 10 + 20), analytics reader and pushdown sources (`ANALYSTOS_ANALYTICS_*`,
   5 + 5 per URL), loader (`ANALYSTOS_LOADER_*`, 2 + 3, lowered from 5 + 5); `*_POOL_MODE=none`
   (NullPool); `ANALYSTOS_DB_TRANSACTION_POOLER` turns psycopg's server-side prepares off.
2. **PgBouncer** in compose (`--profile pooled`) and Helm (`pgbouncer.enabled`, off by default).
3. `tools/registry.gate_agent_write` no longer starts the caller's transaction before opening its own.
4. `semantic/service.save_model` retries a colliding version number in a savepoint.
5. `registries/hypotheses.register_run` locks rows in a fixed order.
6. `build/targets.provision_target` uses `SET LOCAL ROLE` (was a session-level `SET ROLE`).
7. `scripts/load`: app URLs through `ANALYSTOS_LOAD_PG_APP`; workers in their own process group so
   compute-pool children die with them (the interrupted attempt above left 60 orphaned pool processes
   holding ≈ 7 GB, which throttled the next attempt — those numbers were discarded); a failed status
   poll is retried; server-wide connection and free-memory samples.

## Sizing rule this measured

Some paths still open a short transaction while the caller's transaction holds a connection, so a
transaction pooler's **server pool for the control database must exceed the concurrent activity
slots that touch it** (here 4 × (8 analysis + 4 publish + 2 crawl + 2 elt) threads, of which the
analysis ones are busy): 8 deadlocked, 20 timed out, 30 completed. Keep `query_wait_timeout` finite
(compose default 60 s) so an undersized pool becomes a retried error rather than a hang
([operations runbook](../../30-runbooks/02-operations.md#connection-pooling-p4-s05)).
