# P4-02 evidence — BI workspace isolation and container sandbox (2026-09-26)

Host: 4-core Linux 6.18 container (x86_64, cgroup v1, Docker socket), compose Postgres 16 (pgvector),
Superset 4.1.1 (`analystos-superset:4.1.1`). Test databases `analystos_test_p402` /
`analystos_test_dp_p402_analytics` with their own role prefix `aostest_p402_`.

## Hole found and closed

Before this change every workspace's Superset database connected as the shared reader login with
`options=-c role=analystos_r_<ws>`. The reader is a member (`SET TRUE`) of every workspace role, so SQL
run through that connection could switch workspace. Reproduced on the shared `analytics` database:

```
PGOPTIONS="-c role=analystos_r_ws_f4256a0c3335" psql -U analystos_reader analytics
select current_user;                                   -> analystos_r_ws_f4256a0c3335
select count(*) from information_schema.tables where table_schema='src_src_5a1480916f5d';  -> 0
select set_config('role','analystos_r_ws_9a64f2b01762', false);   -> switched (a SELECT: allowed in SQL Lab)
select table_name from information_schema.tables where table_schema='src_src_5a1480916f5d'; -> orders, customer
```

Now each workspace's Superset database connects as its own BI login (`analystos_bi_<ws>`, member of
that workspace's reader role only, `INHERIT TRUE, SET FALSE`, read-only). The same statements are
refused with `permission denied to set role`.

## Sandbox isolation — probes (`tests/unit/test_sandbox_isolation.py`)

Hostile code with the Python policy switched off; each probe on each backend:

| Probe | process (root worker) | process (uid 1000, user namespace) | container (`python:3.11-slim`, `analystos-sandbox`) |
|---|---|---|---|
| egress to 1.1.1.1, host Postgres, docker bridge; DNS; interfaces = `lo` only | denied | denied | denied |
| writes to `/`, `/etc`, `/tmp`, `/var/tmp`, `/dev/shm`, `/usr/lib`, scratch parent; 64 MB into 8 MB scratch | denied | denied | denied |
| worker env var, other processes' `/proc/<pid>/environ` (PID 1 alone), masked secret file | not visible | not visible | not visible |
| CapEff/CapBnd = 0, NoNewPrivs = 1, remount `/` rw, `setuid(0)` | denied | denied | denied |
| fork bomb (pids limit 32) | bounded (`BlockingIOError`), nothing left | bounded | bounded (`--pids-limit`) |
| 2 GB allocation / growing list at 256 MB | `MemoryError` | `MemoryError` | `MemoryError` |
| CPU spin / `sleep(120)` with 2 s budget | killed / timed out | killed / timed out | killed / timed out, container gone |

Gate: `test_gate_fails_closed_when_seccomp_blocks_namespaces` installs a seccomp filter blocking
`unshare(2)` in a fresh interpreter with no sandbox image → `available: false`, `run_python` refused
(`isolation: "unavailable"`). `analystos sandbox-status` on this host: `backend: process, available: true`;
with `ANALYSTOS_SANDBOX_ISOLATION=container` and a missing image: refused with the reason.
`analystos-sandbox` image (built from `deploy/sandbox/Dockerfile`, 995 MB) ran the numeric stack
(numpy/pandas/scipy/sklearn/statsmodels) via `run_python` in container mode.
